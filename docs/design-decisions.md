# 关键设计决策

本文档记录系统中的关键职责划分，以及这些设计如何支持调试、验证和异常处理。

## 1. ESP32只承担网络接入和透明桥接

### 决策

ESP32负责Wi-Fi连接、UDP收发以及UDP数据报与UART数据流之间的转发，不在本地维护独立的车控业务状态，也不负责解释控制命令的最终语义。

### 原因

- 网络接入与安全事务属于不同问题，分离后更容易单独验证；
- 避免PC、ESP32和执行端同时维护多份“当前状态”；
- ESP32固件可以围绕稳定收发、缓冲和错误恢复展开；
- 当链路异常时，可以通过PC–ESP32和ESP32–FPGA分段测试快速定位问题。

### 代价

- ESP32不能在脱离FPGA时独立完成完整业务；
- UART吞吐、缓冲和帧边界处理必须经过专门验证。

## 2. FPGA负责密码和控制事务

### 决策

FPGA位于ESP32和STM32之间，负责调用AES/SM4参考核心、解析安全帧、检查操作码/CRC/序列号、管理车控事务，并处理STM32返回的状态。

### 原因

- 密码处理和协议检查在控制命令进入物理执行端之前完成；
- FPGA可以将密码核心、UART接口和车控状态机组合为明确的数据通路；
- 事务层能够拒绝长度、操作码、CRC、序列号或密码检查失败的请求；
- 返回链路可以复用同一安全边界，对真实STATUS进行校验和响应处理。

### 边界

AES / SM4 算法核心采用公开参考实现；工程重点集中在接口适配、事务状态机、通信集成和验证。

## 3. STM32负责最终执行和失联停车

### 决策

STM32直接控制PWM/GPIO并监测控制链路。如果在规定时间内没有收到有效控制帧，执行端主动停车并将PWM置零。

### 原因

- 最终安全动作应靠近电机执行端；
- 网络断开、PC程序退出或上游事务停滞时，STM32仍能独立进入安全状态；
- 停车机制可以通过STM32直连测试和完整链路测试分别验证；
- 真实状态从执行端生成，便于区分“命令已发送”和“设备已执行”。

## 4. PC只显示经过确认的设备状态

### 决策

PC端不直接把用户点击或已发送命令当作小车实际状态。只有在返回帧完成来源、长度、操作码、解密、CRC和序列号检查后，才更新已确认状态。

### 原因

- 无线发送成功不代表命令已经通过FPGA并被STM32执行；
- 避免界面使用模拟值或命令值冒充真实设备反馈；
- 为超时、重放、乱序和错误响应提供明确处理边界。

## 5. 使用分层测试而不是单一端到端演示

### 决策

验证流程分为软件回归、FPGA单元/RTL验证、综合实现检查和真实硬件测试。不同证据层分别记录，避免把仿真通过直接等同于板级功能通过。

### 原因

- 多设备系统的失败可能来自协议、代码、RTL、综合、接线、供电或版本不一致；
- 分层证据便于定位故障和复现结果；
- 通过commit、固件哈希、bitstream哈希和日志记录，可以区分完整开发基线、资格产物和比赛现场精简配置。
